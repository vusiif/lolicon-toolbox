# 乱码恢复：手动验收

使用最新构建或发布包，进入“文本与编码 → 乱码恢复”。每次粘贴后点击
“智能分析”；原始输入保持不变，结果只能通过复制使用，不会修改文件。

| 测试 | 输入/操作 | 预期 |
|---|---|---|
| 单字节错误解码 | `ä½ å¥½`（中间是不换行空格，完整复制） | 首选候选是 `你好` |
| UTF-8 被当作 GBK | `浣犲ソ` | 首选候选是 `你好` |
| 正常中文 | `正常的中文文本。` | 保留原文，提示没有可靠改进 |
| 正常外语与符号 | `café naïve Straße 😀 ∑ π` | 保留原文 |
| 部分乱码 | `正常前缀：ä½ å¥½` | 包含 `正常前缀：你好`；解释说明按片段处理 |
| 信息丢失 | `你好�`、`??` | 提示可能已丢失信息，不能宣称可靠恢复 |
| 恢复过程 | 展开“查看恢复过程” | 编码路径、逆向校验、异常数、搜索边界与候选对应 |
| 候选切换 | 点击左侧候选卡片 | 仅点击的卡片高亮，右侧预览和恢复过程同步更新；没有结果的卡片不显示，不改原文 |
| 质量评分 | 查看按钮及恢复过程中的分数 | 分数在 0–100 范围内，说明异常密度和缺失信息等依据，不宣称正确概率 |
| 复制 | 选择候选，复制到记事本 | 内容与选中的候选一致 |
| 编辑输入 | 得到结果后修改输入 | 清空旧结果，需要重新分析 |
| 后台任务 | 分析较长文本时切换到 Base64 | 窗口保持可操作，分析完成后仍可返回查看 |
| 取消/关闭 | 长文本分析中取消，或关闭程序 | 不崩溃，不显示已取消/过期任务的旧结果 |
| 语言/主题 | 切换简体、繁体、英文和主题 | 导航、按钮及过程说明同步变化，输入与结果保留 |
| 输入上限 | 超过 1 MiB 的文本 | 明确提示输入过大 |
| 拖入文件 | 把文本文件拖到乱码原文框 | 切换到“文本文件”并分析该文件，不把路径粘贴进输入框 |

“高置信度”是启发式判断，不是数学概率；“可逆”只表示字节路径可验证，
并不保证语义正确。GBK、Big5 等候选可能同样合法，应根据内容选择。
输入中已被替换成 `�` 或问号的部分可能无法找回。

长段落损坏样本：

```text
璇峰皬缁勮礋璐ｄ汉鍦ㄧ兢鍐呮眹鎶ュ綋鍓嶉」鐩繘搴︿互鍙婇亣鍒扮殑闂锛屾柟渚挎寚瀵艰�佸笀鎺屾彙椤圭洰鎯呭喌銆佸強鏃剁粰鍑烘寚瀵煎缓璁�傜鍚勪綅椤圭洰鎺ㄨ繘椤哄埄
```

首选结果应为：

```text
请小组负责人在群内汇报当前项目进度以及遇到的问题，方便指导�师掌握项目情况、及时给出指导建议�祝各位项目推进顺利
```

页面仍须提示信息丢失，恢复过程须说明 `�` 是未知区域，完整逆向校验不能通过。
不要将未知位置猜成“老”或句号：原始字节已经丢失，不能据语境宣称恢复完成。

自动化测试数据位于 `tests/data/mojibake_cases.json`，包含经过字节转换验证的
单次、二次及多语言乱码。只有真实恢复路径可逆的候选才标记完整逆向校验通过。

## 有损 GBK 重建（GBK 被当作 UTF-8 读取后又保存）

典型来源：手机或编辑器用 UTF-8 打开 GBK 文本，把无效字节换成 `�` 后保存。
这类文件里每个 `�` 吃掉了 1–3 个字节，整串换编码不可能还原。本地算法逐字节
重建：凡是恰好构成合法 UTF-8 的字节都还在，搜索能把损坏文本原样重现的 GBK
字节序列，再用由 jieba 词典建的词频模型（`resources/charlm/zh_wordlm.bin`，词的前缀树）挑字。

| 测试 | 输入/操作 | 预期 |
|---|---|---|
| 识别 | 粘贴或打开这类文本 | 首选卡片“重建受损的 GBK 文本”，状态提示检测到受损的 GBK；不再出现“锟斤拷/占쏙옙”一类候选 |
| 证据着色 | 查看预览及下方图例 | 黄色 = 只剩一个字节、由词频推测；红色 □ = 字节全部丢失；未着色 = 两个字节都在 |
| 恢复过程 | 查看恢复过程 | 说明确定/推测/丢失的字数，以及损坏符合哪种 `�` 替换方式 |
| 速度 | 400 KB 左右的文件 | Release 构建数秒内完成，可取消，分析时显示进度条 |
| AI 精修 | 点击“AI 精修（N 段）” | 分段发送（每次 3 段并发），出现“AI 精修版”卡片并随进度更新；蓝色为 AI 补全的字 |
| AI 草稿 | 查看发给 AI 的请求 | 黄色字写成 `〔甲\|乙\|丙…〕`，列出与残留字节相符的至多 5 个字，本地首选在前；`lost_count_exact` 说明 □ 的个数是否确定 |
| 字节校验 | 查看 AI 精修版的恢复过程 | 列出 AI 补全字数和与残留字节矛盾而未采用的字数；AI 不能把字改成与残留字节矛盾的字 |
| 中断续跑 | 精修中点“取消 AI”，再点 AI 精修 | 已校验的段保留，只继续剩余和失败的段 |
| 文件保存 | 文本文件页选中 AI 精修版，另存副本 | 副本内容与预览一致，源文件不变 |

自动化测试在 `tests/TestLossyGbk.cpp`（散文样本 `tests/data/lossy_gbk_prose.txt`，议论文样本
`tests/data/lossy_gbk_essay.txt`，两种 `�` 替换方式都测）。把环境变量 `LOSSY_GBK_SAMPLE`
指向一个真实损坏文件，可额外输出该文件的耗时和字数统计；再把 `LOSSY_GBK_MARKUP` 设为一个
输出路径，可写出第一段发给 AI 的草稿。词频只能
排序，不能证明语义；□ 处的原字没有任何字节留下，AI 补全也只是语境推测。

## 基准测试（TestMojibakeBenchmark）

`tests/data/mojibake_benchmark.json` 收录 100 句本项目自写的简体、繁体、日文、韩文、
英文及混排句子。测试把每句用一种编码保存、再用错误的编码读取（共 15 种组合，
只采用现实中会出现的语言与编码搭配），检查分析器是否把原文排在第一；另检查
正确文本不被“修复”，以及文件按正确编码解码。结果写入构建目录
`tests/mojibake-benchmark.txt`，含每种组合的命中率和前几个失败样例。

| 指标 | 改进前 | 2026-11-08 | 测试下限 |
|---|---|---|---|
| 正确文本保持不变 | 100% | 100% | 100% |
| 损坏文本首选即原文 | 61.3% | 95.4% | 93% |
| 损坏文本原文在前五 | 98.4% | 100% | 100% |
| 文件首选编码正确 | 58.9% | 99.6% | 97% |

改进来自“常用字”评分：GB2312 一级、Big5 常用字、JIS 第一水准和 KS X 1001
韩文音节都是按使用频率选出的，直接由编码表推出，不依赖外部字表。乱码多落在
这些集合之外（例如 UTF-8 续字节落在 GBK 扩展区），每个生僻字计一处异常。另有
弱证据：中文编码解出假名、EUC-KR 解出汉字、汉字之间夹空格。旧版写死的
“浣犲、璇峰”等特征片段已删除。

剩余的失败多是两三个字的短词，同一串字节在两种编码里都是常用字，例如 GBK 的
“你好”在 Big5 中读作“斕疑”、“谢谢”读作西里尔字母“лл”。只凭字符本身无法区分，
此时按简体中文优先的固定次序排列，其他候选仍在前五名内。修改评分后先跑这个
基准；下限只能上调，不能为了让改动通过而下调。

## AI 辅助验收

1. 在“设置 → AI 接口”填写服务商的基础地址（通常以 `/v1` 结尾）和密钥，点击“获取模型”。应出现模型 ID 列表，选好后保存；也可手动输入模型 ID。不要填写 `MiMo` 这样的品牌名称。保存不会联网，重启后配置应保留，密钥应仍为掩码显示。
2. 粘贴上述长段落并先做本地分析。仅本地分析时不应发出 AI 请求；尚未分析或没有模型配置时，AI 按钮不可用。
3. 点击“AI 深度分析”。按钮旁显示的目标地址和模型必须与设置一致。原文及本地候选会发送给该服务，可能产生服务商费用。
4. 回复成为候选列表最上方的“AI 建议”卡片并自动选中，本地候选不变。在恢复过程中检查模型说明是否区分确定的编码恢复和根据语境推测的内容；“老”或句号之类补全不能标成字节恢复成功。
5. 分别选中 AI 卡片和本地候选，点击“复制结果”，粘贴到记事本，确认复制的是当前选中卡片的正文。
6. 请求中点击“取消 AI”，再重试。修改输入或 API 设置应取消旧请求、清空旧建议；关闭窗口不应崩溃。
7. 用无效密钥、无权限模型或错误地址测试失败提示，本地候选应保留。若模型未按 JSON 格式回复，应提示格式问题，可重试或更换模型。
8. 分别检查简体、繁体、英文及两种主题。长页面应可滚动，API 密钥不能出现在日志、截图明文或错误提示中。
9. 点击 AI 分析后，应看到已等待秒数。开始生成后应出现“正在接收 AI 回复”及字符数量；若服务返回思考内容，只显示思考状态和数量。最终结果须在完整回复校验后显示，不能长时间停留在没有进度的固定提示上。

官方 MiMo 地址会使用 `thinking.type=disabled`，减少该任务的推理等待。其他服务不发送此专属字段。

AI 输入上限 16 KiB，请求上限 128 KiB，回复上限 1 MiB，超时 90 秒。远程 API 要求 HTTPS，本机服务可用 HTTP。
程序请求 `/chat/completions`，不自动跟随重定向。AI 建议不是确定原文，真实模型效果由你配置服务后亲自验收。

模型列表额外检查：获取时不上传乱码；取消、修改地址或密钥应清空旧列表并取消未完成请求。重复获取应保留当前输入的模型 ID。
接口返回 404/405/501、无效 JSON 或空列表时应明确提示，手动输入仍可用；列表可能包含非文本聊天模型，请选择服务商支持的聊天模型。
